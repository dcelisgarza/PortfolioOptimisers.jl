PortfolioOptimisers.AbstractSeparationAlgorithm — Type
abstract type AbstractSeparationAlgorithm <: AbstractAlgorithm

Abstract supertype for all separation algorithms.

A separation algorithm states how far apart two assets are in a network, and how far apart two related assets can be. One object answers the two questions through three functions:

  • separation_graph builds the structure that the member measures.
  • separation_matrix reads the dense assets × assets separations from that structure.
  • separation_budget resolves the budget. A pair further apart than the budget is unrelated.

The family is open. A new member is a struct and one method of each function.

The two questions share a unit. A hop count has its budget in hops, and a weighted path length has its budget in the units of the distance estimator. A budget apart from the rule that measures it is a number with no unit. So the budget is a field of the member, not of NetworkEstimator.

The structure and the measurement are two functions

The function that measures takes the structure, not the estimator that builds it. separation_matrix(sep, g) is the interface, and separation_matrix(sep, nte, X) is a wrapper that calls separation_graph first. calc_weighted_adjacency_graph has the same two entry points for the same reason. The structure is expensive, and a caller often has one already.

Under VariationInfoDistance, the structure takes 98% of the runtime of clusterise. A consumer that resolves a budget rule and also measures the separations must build the structure once and pass the graph to both functions.

A test or an extension also calls separation_matrix(sep, g). Every structure that a shipped estimator builds is connected, because it is a spanning tree or a PMFG. Only a graph that a caller gives can be disconnected and carry the unreachable sentinel.

Two more functions

resolve_separation changes a member whose budget is a rule into a member whose budget is a value. Every consumer calls it before the other two functions. It asks nothing new about the network. The fallback on this type returns a member with a numeric budget unchanged, so an extension inherits it and writes no method.

is_related applies the budget to one entry of the separation matrix, after the sentinel test of is_reachable. Each is one generic method on this type, because the rule is the same in every unit. A related pair is not the sentinel, and it is not further apart than the budget.

A member whose routine reports a different sentinel overrides is_reachable alone. Every consumer that applies a budget calls these two functions and writes no comparison of its own. So the rule of "The unreachable sentinel" of separation_matrix stays inside one interface.

The two shipped members accept a rule in the budget field, through HopCountValue and PathLengthValue. A caller who cannot state the budget in advance gives the rule that calculates it. The library resolves the rule where the data is available, because a rule needs the data. For this reason separation_budget refuses an unresolved member and does not return a function.

Separation is not decay

AbstractSeparationDecayAlgorithm changes a separation into a score. This family calculates the separation and its budget. sep decides which pairs are related, and every consumer of a network needs that. decay decides how strongly a pair is related, and only the feature producer needs that number. So sep is a field of NetworkEstimator and decay is a field of Proximity.

The name does not say graph

The name of the family says nothing about graphs. A taxonomy depth is also a separation. The name leaves room for a member that measures one, and AbstractGraphSeparationAlgorithm does not.

PortfolioOptimisers.HopCountAlgorithm — Type
abstract type HopCountAlgorithm <: AbstractAlgorithm

Abstract supertype for all rules that compute a hop count from the network and the data.

The caller usually states a HopCount budget as a number, but the budget can also be a rule. A subtype of HopCountAlgorithm is a callable struct in the n field. resolve_separation calls it with the network estimator and the data matrix.

A rule lets the budget follow a universe whose size the caller does not know in advance. Examples are a cross-validation fold and a subproblem of a meta optimiser such as NestedClustered.

The extension contract

A subtype defines one method, the functor:

(rule::MySubtype)(nte::AbstractNetworkEstimator, X::MatNum, g::Graphs.AbstractGraph;                  dims::Int = 1, kwargs...) -> Integer

g is the structure that separation_graph built for the separation that holds the rule. The rule reads what it needs from g through separation_matrix, which takes g directly, so the rule builds no structure. It still runs the traversal of all pairs, as resolve_separation states.

nte holds the separation, and X is the data that g comes from. The shipped rule reads neither. An extension reads them to get what the graph does not hold, for example the distance estimator, the number of observations or a covariance.

The return value must be an Integer. The return type of a functor is not part of its signature, so the type system cannot state this requirement. resolve_separation checks the value instead. Three readers use 0:n as a count of matrix powers, and 0:1.5 drops a power with no error.

The same field also accepts a bare Function, which has the same requirement. The constructor does not check it. Subtype this type instead when the rule has parameters, because the struct holds them, prints them and compares equal by them.

PortfolioOptimisers.PathLengthAlgorithm — Type
abstract type PathLengthAlgorithm <: AbstractAlgorithm

Abstract supertype for all rules that compute a path-length budget from the network and the data.

This is the PathLength counterpart of HopCountAlgorithm. A subtype is a callable struct in the dmax field. resolve_separation calls it with the network estimator, the data matrix and the structure that it built from them.

The two families have different return types, so they are two types. The split lets resolve_separation check each return type. A hop count must be an Integer. A path-length budget is in the units of the distance estimator, so it can be any Number.

The extension contract

A subtype defines one method, the functor:

(rule::MySubtype)(nte::AbstractNetworkEstimator, X::MatNum, g::Graphs.AbstractGraph;                  dims::Int = 1, kwargs...) -> Number

g is the structure of separation_graph. Under a PathLength its edges carry distances on both branches. The same field also accepts a bare Function, which has the same requirement. The constructor does not check it.

A rule must return a Number, and nothing is not a Number. nothing in the dmax field means the observed diameter. The caller states it in place of a rule. A rule cannot ask for the diameter with nothing, because the field states that value already. If a rule returns nothing in error, resolve_separation throws an ArgumentError and does not give the largest ball. So PathLengthValue holds the rules and the numbers, and the field is an Option of it.

PortfolioOptimisers.AbstractSeparationDecayAlgorithm — Type
abstract type AbstractSeparationDecayAlgorithm <: AbstractAlgorithm

Abstract supertype for all separation decay algorithms.

A separation decay changes a separation d >= 0 into a score. The separation is how far apart two assets are in the structure that the caller reads. separation_decay applies the decay. The family is open. For a different fall-off, define a member and a separation_decay method for it. AbstractSimilarityMatrixAlgorithm and distance_to_similarity have the same pattern.

d is a real separation and not an integer hop count. So one family serves an unweighted graph, where a hop count is a real with an integer value, and each structure whose separation is continuous.

The contract

  • f has a value for every d >= 0.
  • f(0) > 0, and f(0) is the largest value. A decay must put an asset at the top of its own scale. If not, the result is a structural equivalence matrix, not a proximity matrix. See "Why the diagonal includes self" of PhylogenyPanel.
  • f is monotone non-increasing in d.
  • The contract does not ask f to reach zero. The budget truncates, and the decay does not. The consumer applies the budget, which is separation_budget of the AbstractSeparationAlgorithm in scope. The decay shapes the fall-off inside the budget. An exponential never reaches zero, so one parameter cannot set the budget and the fall-off.
  • f(d) >= 0 for 0 <= d <= dmax. The score of an unreachable pair is 0. A negative score inside the budget puts a reachable pair below an unreachable pair on the scale of the producer.

The last clause does not say that a signed score is always wrong. The feature matrix accepts signed values by decision, and assert_metric_domain checks non-negativity for each metric at the consumer. The clause applies to the producer alone. It asks for non-negativity and not strict positivity, because a decay that falls to zero says that the pair is unrelated. An unreachable pair says the same.

The clause applies inside the budget alone, for two reasons. First, the sign outside the budget has no effect, because the consumer tests is_related first and does not evaluate the decay there. Second, the default of the family breaks the wider clause. LinearDecay is zero at d = dmax + 1 and negative above it. A clause on all d >= 0 needs a max(0, ⋅) floor, which is a second truncation inside the decay.

So a zero in the feature matrix means that the pair is unrelated. The pair is unreachable, it is outside the budget, or the decay fell to zero. A consumer of the feature matrix cannot tell these cases apart. No shipped member gives zero inside the budget. For the shipped members, a zero means unreachable or outside the budget.

The budget is an argument, not a field

separation_decay takes the budget in scope as its third argument, dmax. A member can ignore it, and only LinearDecay reads it, to set f(0). The member does not hold the budget, so the budget and the decay cannot disagree. The AbstractSeparationAlgorithm is the one place that holds the budget. A decay algorithm cannot see the budget when the caller constructs it. ExponentialDecay sets the contrast between an asset and its neighbour with its own rate, and adds no second truncation inside the decay.

Enforcement

The fallback assert_separation_decay on this type probes a member and enforces the contract. The shipped members satisfy the contract by construction, and their method of that function does nothing. So an extension that defines no method of assert_separation_decay gets the probe.

PortfolioOptimisers.is_reachable — Function
is_reachable(sep::AbstractSeparationAlgorithm, d::Number)

Is d a separation at all, or the sentinel an unreachable pair carries?

separation_matrix does not repair the sentinel of the routine that it calls. This test tells a measured separation from a missing one. It is one generic method on AbstractSeparationAlgorithm, because one expression covers the two shipped sentinels. A member whose routine reports a different sentinel overrides this method, and it inherits is_related unchanged.

The test is not isfinite alone, and not typemax alone

Each clause rejects a sentinel that the other clause accepts.

  • isfinite is true for every Integer. Alone, it accepts the typemax(Int) of HopCount, and ReciprocalDecay overflows at that value.
  • typemax of a Float64 is Inf, so the comparison also rejects the sentinel of PathLength. isfinite rejects a NaN. No shipped path gives a NaN, and a NaN compares false with every budget.

Algorithm

  1. Test isfinite(d). This rejects a NaN and the Inf of PathLength.
  2. Compare d with typemax(typeof(d)). This rejects the typemax(Int) of HopCount, which step 1 accepts.
  3. Return reachable, the conjunction of the two tests. && short-circuits, so step 2 runs only on a finite d.

Arguments

  • sep: Separation algorithm. The shipped members do not read it. An extension whose routine reports a different sentinel dispatches on it.
  • d: One entry of a separation matrix from separation_matrix.

Returns

  • reachable::Bool: true when d is a measured separation.

PortfolioOptimisers.is_related — Function
is_related(sep::AbstractSeparationAlgorithm, d::Number, dmax::Number)

Does a separation of d count as related under a budget of dmax?

This is the one function that applies the budget to an entry of a separation matrix. A related pair is reachable, and it is not further apart than dmax. Each consumer that compares a separation with a budget calls this function and writes no comparison of its own. The PathLength branch of phylogeny_matrix and the Proximity method of phylogeny_features call it.

The reachability test comes first

d <= dmax alone is not sufficient. It rejects the two shipped sentinels only because of the two shipped budgets. separation_budget clamps a PathLength budget to the observed finite diameter, and a HopCount budget has a cap far below typemax(Int). is_reachable makes the rejection part of the predicate. A budget at the largest value of its unit then still excludes an unreachable pair.

The caller must still short-circuit

A consumer that scores the separation must put the score inside a branch that short-circuits. Write is_related(...) ? separation_decay(...) : zero(...), and do not use ifelse. An ifelse evaluates the two branches. ReciprocalDecay overflows 1 + d at typemax(Int), and a fractional power then gives a DomainError. The predicate holds the rule, and the call site must not evaluate the score of an unrelated pair.

Algorithm

  1. Call is_reachable on sep and d, which gives the reachability test. This test runs first, so the function rejects a sentinel at each value of dmax.
  2. Compare d with dmax, which gives the budget test.
  3. Return related, the conjunction of the two tests. && short-circuits, so step 2 runs only on a reachable d.

Arguments

  • sep: Separation algorithm, which the function passes to is_reachable.
  • d: One entry of a separation matrix from separation_matrix.
  • dmax: Separation budget in scope, from separation_budget. It has the units that sep measures in, so the two arguments come together.

Returns

  • related::Bool: true when the pair is reachable and inside the budget.

PortfolioOptimisers.assert_separation_decay — Function
assert_separation_decay(dk::AbstractSeparationDecayAlgorithm, ds, dmax::Number)
assert_separation_decay(dk::Union{LinearDecay, ExponentialDecay, ReciprocalDecay}, ds,
                        dmax::Number)
assert_separation_decay(::Nothing, ds, dmax::Number)

Check that a separation decay satisfies its contract over the separations that the caller will score.

The fallback probes the decay. It evaluates separation_decay over ds and checks four properties:

  • Each value is finite.
  • f(0) is strictly positive, and it is the largest value.
  • The values are monotone non-increasing.
  • No value is negative.

The three shipped members and nothing satisfy the contract by construction, and their method does nothing. So the probe costs nothing for a shipped member, and it checks each extension.

The probe is cheap where the library uses it, because ds is small and the loop after the probe is large. Proximity passes 0:dmax. Under HopCount, this range holds every separation that the assets × assets loop can score, in dmax + 1 evaluations. Under a budget that is not an integer, the same range is a sample with a step of one. A continuum permits only a sample, and the checks below need no more.

The non-negativity check has one more evaluation at d = dmax, also when ds does not contain dmax. It is the counterpart of the evaluation of f(0) before the loop. If the decay is monotone, f(dmax) >= 0 gives f(d) >= 0 for every d in [0, dmax]. So the check holds over the continuum, also when ds is a sample, as it is for weighted path lengths. The endpoint does not help the monotonicity check, which stays a sample.

Algorithm

These are the steps of the probe in the fallback. The method on the three shipped members and on nothing runs none of them.

  1. Score the separation zero(dmax) with separation_decay, which gives f0, the top of the scale.
  2. Check that f0 is finite and strictly positive.
  3. If ds is not sorted, sort it, so that step 5 reads the separations in increasing order.
  4. Set fp, the score of the previous separation, to f0.
  5. For each d of ds, score it with separation_decay, which gives f. Check that f is finite and not more than f0. Check that f is not more than fp. Check that f is non-negative. Set fp to f.
  6. Score dmax, which gives fmax, and check that fmax is non-negative. This is the endpoint that the paragraph above states. Step 5 does not always reach it.
  7. Return nothing.

Arguments

  • dk: Separation decay algorithm.
  • ds: Separations to probe, in any order. Each separation must be in [0, dmax], because the loop after the probe scores no separation outside the budget.
  • dmax: Separation budget in scope. The function passes it to separation_decay, and also probes it as an endpoint.

Validation

  • Every probed value is finite.
  • f(0) > 0.
  • f(0) >= f(d) for every probed d.
  • The probed values are monotone non-increasing in d.
  • f(d) >= 0 for every probed d, and at d = dmax whether or not it was probed.

Returns

  • nothing.
