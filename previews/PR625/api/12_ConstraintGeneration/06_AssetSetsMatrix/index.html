PortfolioOptimisers.UniverseSets — Type
struct UniverseSets{__T_xkey, __T_uxkey, __T_fkey, __T_ufkey, __T_zkey, __T_dict} <: AbstractEstimator

Declares the universes a portfolio problem is written against, and any groupings or partitions of them.

Constraint generation and the estimator routines read it to expand group references, to map a group name to its member list, and to validate membership.

It declares every axis it carries: xkey/uxkey for assets, fkey/ufkey for factors, and zkey for features. Assets are the primary axis — haskey(dict, xkey) is required, and it is the axis a view slices. The factor and feature axes are optional: requiring either would invalidate every sets object built for a problem with no factor model or no feature program, so a consumer that needs one and does not find it throws at the point of need rather than at construction.

If a key in dict starts with the same value as xkey, it means that the corresponding group must have the same length as the asset universe, dict[xkey]. This is useful for defining partitions of the asset universe, for example when using asset_sets_matrix with NestedClustered.

If a key in dict starts with the same value as uxkey, it identifies a unique-entry group variant. The corresponding xkey-prefixed group must exist in dict with the same length as the asset universe, and is used to match each asset to a unique entry from the uxkey-prefixed group. This enables constraint generation using unique entries even in NestedClustered optimisations.

The fkey/ufkey prefixes mean the same thing on the factor axis, but they buy something different. On the asset side the conventions serve views; factors are never sliced by an asset index, so on the factor side they buy length validation at construction and one shared mental model.

zkey has no prefix convention at all, and that asymmetry is the point. xkey and fkey each have a unique-entry sibling because each names an axis that partitions are written over; nothing is written over the feature axis. A graded feature program's taxonomy keys are xkey-prefixed and asset-length, and its column nodes are named directly out of the flat list dict[zkey]. So zkey carries exactly one rule — allunique(dict[zkey]), so ReturnsResult's own uniqueness check cannot be reached with a duplicate — and no length rule whatever.

A key matching none of the four prefixes is a plain group: expanded by name and axis-blind, which is why a factor group needs no machinery of its own.

Fields

  • xkey: Key in dict identifying the primary asset list. Required, and the axis a view slices.
  • uxkey: Key prefix for unique-entry asset group variants in dict.
  • fkey: Key in dict identifying the factor list. Optional — a consumer that needs it and does not find it throws at the point of need.
  • ufkey: Key prefix for unique-entry factor group variants in dict. Validated at construction, never recomputed by a view.
  • zkey: Key in dict identifying the declared feature axis — the node list a graded feature program writes its columns against. Optional, like fkey, and it carries no prefix convention: nothing is partitioned over the feature axis, so it has no unique-entry sibling and no length rule beyond allunique.
  • dict: Dictionary mapping group identifiers to member labels.

View parameters

UniverseSets defines its own port_opt_view method rather than deriving one from field tags.

  • The method reads the asset index alone. It drops every further positional argument, because no axis but the asset axis is sliced.
  • Every xkey-prefixed entry of dict is sliced to the selected assets, and every uxkey-prefixed entry is rebuilt from the sliced partition it names.
  • The fkey-, ufkey- and zkey-prefixed entries, and every plain group, are carried through unchanged. port_opt_view states why each axis is exempt.
  • The five key prefixes are carried through unchanged, so the viewed value declares the same axes as the original.

Read the taxonomy column sets.dict[key], checking that the key exists.

The sibling of factor_universe and feature_universe for a group name key, and written for the same reason: one shared helper whose message names the key and says what to do about it, so every consumer of a caller-supplied taxonomy key fails the same way. PortfolioOptimisers.asset_sets_matrix — Function
asset_sets_matrix(
    smtx::AbstractString,
    sets::UniverseSets
) -> LinearAlgebra.Transpose{Bool, BitMatrix}

Construct a binary asset-group membership matrix from asset set groupings.

asset_sets_matrix generates a binary (0/1) matrix indicating asset membership in groups or categories, based on the key or group name smtx in the provided UniverseSets. Each row corresponds to a unique group value, and each column to an asset in the universe. This is used in constraint generation and portfolio construction workflows that require mapping assets to groups or categories.

Algorithm

  1. Read the taxonomy column all_sets from sets.dict[smtx], through taxonomy_column.
  2. Check that all_sets has the length of the asset universe.
  3. Take unique_sets = unique(all_sets), the distinct group values in order of first appearance. Each one defines a group, and the order of unique_sets is the order of the groups in the result.
  4. For each group val of unique_sets, write the indicator all_sets .== val into column i of a BitMatrix A, giving an assets × groups matrix.
  5. Return transpose(A), which turns the groups into the rows and the assets into the columns.

Arguments

  • smtx: The key or group name to extract from the asset sets.
  • sets: A UniverseSets object specifying the asset universe and groupings.

Validation

  • haskey(sets.dict, smtx), via taxonomy_column.
  • Throws an AssertionError if the length of sets.dict[smtx] does not match the asset universe.

Returns

  • A: The transpose of a BitMatrix, of size (number of groups) × (number of assets), where A[i, j] == 1 if asset j belongs to group i. The orientation is groups × assets, the opposite of the assets × features matrix asset_sets_features builds out of the same blocks. The row order is unique(sets.dict[smtx]), the distinct group values in order of first appearance, which is what makes asset_sets_feature_names line up with the block this matrix contributes.

Examples

julia> sets = UniverseSets(; xkey = "nx",                           dict = Dict("nx" => ["A", "B", "C"],                                       "nx_sector" => ["Tech", "Tech", "Finance"]));julia> asset_sets_matrix("nx_sector", sets)2×3 transpose(::BitMatrix) with eltype Bool: 1  1  0 0  0  1

PortfolioOptimisers.assert_feature_keys — Function
assert_feature_keys(vals::AbstractVector{<:AbstractString})

Assert that a list of taxonomy keys can produce a graded feature matrix.

Shared by asset_sets_features and AssetSetsFeatures, so the estimator rejects a bad key list at construction and the bare entry point rejects it at the call, from one encoding of the rule.

Arguments

  • vals: Group name keys to stack into the feature axis.

Validation

  • length(vals) >= 2. Two keys is a floor, not a style preference: every Distances.jl semimetric is invariant to permuting coordinates, so a one-hot feature matrix — which is what a single partition gives — can only distinguish "same group" from "different group". Raises an ArgumentError.

Returns

  • nothing.

PortfolioOptimisers.AbstractFeatureValue — Type
abstract type AbstractFeatureValue <: AbstractAlgorithm

Abstract supertype for markers that reinterpret a value in a graded feature program.

A bare Number in asset_sets_features' pair grammar sets a cell, absolutely. A marker says the number means something else, resolved against the cell's natural value by resolve_feature_value. Scale is the sole member; the family is open so a second reading can be added without touching the resolver. The reading is carried by a marker rather than by position — a top-level number scaling and a nested one setting — because position is invisible on a one-hot taxonomy, where the natural value is always 1.0 and the two readings coincide, and it diverges silently the moment a taxonomy carries numbers, which is exactly what the graded grammar adds. A marker makes the reading something the caller writes down.

All concrete subtypes should subtype AbstractFeatureValue.

Interfaces

In order to implement a new concrete type that works seamlessly with the library, subtype AbstractFeatureValue and implement the following methods:

resolvefeaturevalue

  • resolve_feature_value(v::AbstractFeatureValue, natural::Number) -> Number: Reinterpret v against the cell's natural value, returning the number the program writes into the cell.

Arguments

  • v: The concrete subtype instance.
  • natural: The cell's natural value: the asset's own number for a numeric taxonomy key, 1.0 when the row belongs to the node and 0.0 when it does not.

Returns

  • z::Number: The value written into the cell.

Examples

PortfolioOptimisers.Scale — Type
struct Scale{__T_val} <: AbstractFeatureValue

Multiply a cell's natural value by val, rather than setting the cell to val.

Scale scales the key's own datum, never the value already accumulated in the cell. At the top level of a program there is no accumulated value — the matrix starts at zero, and scaling zero is useless — so the only coherent referent is the underlying datum.

Mathematical definition

\[\begin{align} v &= a \, n\,. \end{align}\]

Where:

  • $v$: Value the program writes into the cell.
  • $a$: Multiplier the marker carries.
  • $n$: Natural value of the cell. It is the asset's own number when the taxonomy key's data are numbers — nx_esg at 0.30, 0.80, 0.50 — and it is $1$ when the row belongs to the node the target named, whether that node is a one-hot key, an asset or a group member, and $0$ when it does not.

A cell whose natural value is $0$ stays $0$ however large $a$ is, so scaling a cross edge gives zero: "C" => ["nx_country" => "US" => Scale(0.3)] scales C's US membership, and C is UK. Use a bare number to set a cross edge.

Fields

  • val: val: Multiplier applied to the cell's natural value.

Stack taxonomy memberships into an assets × features feature matrix.

asset_sets_features concatenates one asset_sets_matrix block per key in vals, transposed to assets-major, into the exogenous feature matrix FeatureDistance consumes. Feature k reads "belongs to group k", so two assets are close when they are classified together across many taxonomies.

This is the exogenous feature source: a sector, industry or country classification is structure that return correlations do not contain, which is exactly what a feature distance exists to bring in. Every other producer in the library derives Z from the returns.

Mathematical definition

Every key names a partition of the asset universe, so each asset lands in exactly one group per key and every row carries exactly $L$ ones. The rows therefore all have the same norm, and the cosine similarity of two rows is their count of shared classification levels divided by $L$:

\[\begin{align} \sum_{k} z_{i,\,k} &= L\,, \\ \lVert \boldsymbol{z}_{i} \rVert &= \sqrt{L}\,, \\ \cos(i,\,j) &= \frac{\boldsymbol{z}_{i}^\intercal \boldsymbol{z}_{j}}{\lVert \boldsymbol{z}_{i} \rVert \lVert \boldsymbol{z}_{j} \rVert} = \frac{s_{i,\,j}}{L} \in [0,\,1]\,. \end{align}\]

Where:

  • $\boldsymbol{z}_{i}$: Feature vector of asset $i$, its row of the feature matrix.
  • $z_{i,\,k}$: Feature $k$ of asset $i$. It is $1$ when asset $i$ belongs to the group that feature $k$ names, and $0$ when it does not.
  • $L$: Number of group name keys stacked into the feature axis.
  • $s_{i,\,j}$: Number of groups that assets $i$ and $j$ share.

The identity is exact and needs no standardisation, which no other producer of a feature matrix can claim. Its reading depends on how the keys relate, and both readings are useful:

  • Nested (sector ⊃ industry ⊃ sub-industry): two assets share a level only if they share every coarser one, so $s_{i,\,j} / L$ counts the classification levels they agree on — a depth-graded relatedness.
  • Crossed (sector + country): the keys are independent, so the same count reads as how many independent attributes two assets happen to share.

Algorithm

  1. Check the key list with assert_feature_keys.
  2. For each key of vals, in order, build that key's groups × assets block with asset_sets_matrix.
  3. Transpose each block to assets × groups, which is the orientation of the result.
  4. Concatenate the transposed blocks along the feature axis, in the order of vals, and convert the concatenation to Float64, giving Z.

Arguments

  • vals: Group name keys in sets.dict, at least two (see assert_feature_keys). A key that a view must reach carries the sets.xkey prefix — "nx_sector", not "sector" — because an asset view of a UniverseSets slices the groups prefixed by sets.xkey and leaves the rest alone.
  • sets: A UniverseSets object specifying the asset universe and groupings.
  • strict: Accepted for a uniform interface with the graded method and ignored. strict governs name resolution, and on this path every name is a sets.dict key whose absence is an unconditional KeyError from taxonomy_column — there is no soft failure for it to govern.

Validation

  • length(vals) >= 2 and allunique(vals) (see assert_feature_keys).
  • Each key exists in sets.dict and has the length of the asset universe (enforced by asset_sets_matrix). An unprefixed key under an asset view therefore does not fail silently: the sliced universe no longer matches the unsliced group, so this length check throws on the next call.

Returns

  • Z::Matrix{Float64}: An assets × features matrix, Z[i, k] == 1 when asset i belongs to group k. The feature count is the total number of distinct group values across every key. The orientation is assets × features, the transpose of the groups × assets matrix asset_sets_matrix returns, and the column order is each key's unique group values in order of first appearance, concatenated in the order of vals — the order asset_sets_feature_names names. The element type is dense Float64 rather than the BitMatrix asset_sets_matrix returns, so AngularDist keeps its BLAS gemm path.

asset_sets_features(vals::AbstractVector{<:Pair}, sets::UniverseSets;

Resolve an ordered edge-authoring program into an assets × features matrix over the declared feature axis sets.dict[sets.zkey].

This is the graded contract. The group-name-key method above is the degenerate case of it — a partition stack with every written cell at 1.0 — and the two are separated by dispatch on vals' element type, so today's callers, today's matrix and today's "<key>=<group>" names are untouched.

The accepted cost of bare node names is that a nested taxonomy with a repeated value is inexpressible in graded mode. With nx_industry and nx_subindustry both containing IntegratedOil, both land on the one bare node and the later entry overwrites the earlier — harmless under one-hot, where both wrote 1.0, silently lossy under grading. The group-name-key method above qualifies its names and stays the tool for that case.

Algorithm

  1. Check that vals is not empty.
  2. Read the asset universe nx from sets.dict[sets.xkey], which indexes the rows of the result.
  3. Read the declared feature axis nz through feature_universe, which indexes the columns of the result.
  4. Allocate Z, a zero length(nx) × length(nz) matrix.
  5. Build zidx, the map from a node name to its column of Z, and pool, the suggestion pool, through feature_program_candidates.
  6. Apply each entry of vals in order with feature_entry!, giving the written Z. Every write is a pure overwrite, so a later entry replaces an earlier one and last wins — repeating a key is the point, not a mistake, which is why allunique does not carry into this path.

Arguments

  • vals: The ordered program. Its terms follow the grammar

    entry  := rowsel => targets                    # row scope, then explicit columns
        | taxkey [=> group] => value           # diagonal: those rows, their own membership
rowsel := asset | group | taxkey [=> group]
target := taxkey [=> group] => value | asset => value | group => value
value  := Number                               # sets, absolutely
        | <:AbstractFeatureValue               # Scale(x): x × the key's natural value

    where targets is one target or a vector of them. Every target names its column in full: there is no ambient scope and no fallback chain, because "UK" inside a nx_country entry would otherwise be resolved as a country by proximity rather than by what the caller wrote, and UK is also a real ticker. Nodes are named plainly — "Tech", "US", "esg" (a numeric key with sets.xkey * "_" stripped), "A" for an asset node — because the caller authored the axis and qualifying it would make them write the prefix twice.

  • sets: A UniverseSets whose dict declares the feature axis under sets.zkey.

  • strict: Whether an unresolvable name throws instead of warning.

Validation

  • !isempty(vals). Raises an IsEmptyError: a program with no entries can only produce the all-zero matrix, which declares every asset identical. Non-emptiness is the only unconditional structural refusal.
  • haskey(sets.dict, sets.zkey) (see feature_universe).
  • A malformed entry — a term that matches no production of the grammar above — throws an ArgumentError whatever strict says, because there is no reading of it to fall back to.
  • strict governs names only. An unknown node, asset or group warns with a did_you_mean suggestion, and throws under strict.
  • Nothing else structural is refused. An all-zero row is legal, and is the one genuine silent-wrongness case grading opens: an asset no entry touches has a zero row, and FeatureDistance's zero-norm convention declares zero rows mutually identical, so forgotten assets cluster together at distance 0. A one-column matrix is legal too: assert_feature_keys' two-key floor is a property of stacking partitions and does not carry here.

Returns

  • Z::Matrix{Float64}: An assets × length(sets.dict[sets.zkey]) matrix, zero-initialised and then written by the program. The orientation is assets × features, the same as the group name key method's and the transpose of the groups × assets matrix asset_sets_matrix returns. The columns are the declared axis sets.dict[sets.zkey], in the order the caller wrote it.

The declared axis buys two things a derived axis cannot. The first is column order: a Dict has none, so without a declared list the feature axis would be whatever order the taxonomy happened to iterate in. The second is fold invariance: size(Z, 2) does not change under an asset view, because port_opt_view(::UniverseSets, i, args...) passes zkey through — the axis is authored, not summarised. This is the exact opposite of the group-name-key path, and both are documented because both are true. The cost is accepted: an asset node whose asset a view dropped survives as an all-zero column, benign for every blessed metric except Distances.CorrDist, which centres each row.

feature_rows(sel, sets::UniverseSets, nx, pool, strict::Bool) -> Option{Vector{Int}}

Resolve a non-taxonomy row selector — an asset or an asset group — to row indices, or nothing when the name does not resolve.

Taxonomy keys are handled by the caller, because the sets.xkey prefix rule settles them before any lookup. What is left is exactly estimator_to_val's precedence, asset first and then group, resolved by the shared resolve_axis_name, with the factor axis refused between them so a factor-length list is diagnosed by name rather than by an eventual length mismatch. The factor test therefore runs before the resolution, not after: a factor key that is also a sets.dict key would otherwise expand to factor names and be reported as a group of missing assets.

Algorithm

It recognises the grammar's rowsel production for a name that is not a taxonomy key. It writes no cell itself: it fixes the row scope the targets then write in.

  1. When sel is no asset name and is_feature_factor_key holds, drop the term through feature_factor_key_msg and return nothing.
  2. Resolve sel with resolve_axis_name, asset first and then group. When it resolves to neither, drop the term through feature_unknown_name_msg and return nothing.
  3. Turn the resolved members into row indices with axis_name_indices, diagnosing a member that names no asset through missing_group_assets_msg.

Arguments

  • sel: The row selector the entry wrote.
  • sets: A UniverseSets object specifying the asset universe and groupings.
  • nx: The asset universe, sets.dict[sets.xkey], which indexes the rows of Z.
  • pool: The suggestion pool of feature_program_candidates.
  • strict: Whether an unresolvable name throws instead of warning.

Returns

  • rows::Option{Vector{Int}}: The row indices sel selects, or nothing when the name resolves in no namespace.

PortfolioOptimisers.feature_target! — Function
feature_target!(Z::Matrix{Float64}, rows, target::Union{<:Pair, <:AbstractVector{<:Pair}}, sets::UniverseSets, nx, nz, zidx, pool,
                strict::Bool) -> Nothing

Apply the grammar's target production inside an already-resolved row scope, singly or over a vector.

Every target names its column in full, so this reads left to right with no ambient state: a taxonomy key with a group value names that value's node, a numeric taxonomy key names its own node, an asset names its own node, and a group expands to one node per member. The natural value is the row's membership of the node the target named — which is why scaling a cross edge gives zero.

Algorithm

It recognises the grammar's target production inside an already-resolved row scope. The vector method applies the steps below to each element in turn, and the fallback method throws feature_grammar_msg for a term that is no Pair.

  1. Split the target into its left half k and its right half rest.
  2. When k is a taxonomy key (is_feature_taxonomy_key) and rest is g => v, write the node g names. The natural value of a row is 1.0 when that row's entry equals g and 0.0 when it does not. A v that is no value throws feature_grammar_msg.
  3. When k is a taxonomy key and rest is a value, write the key's own node, k with sets.xkey * "_" stripped, at the row's own number. A categorical key throws instead, because the bare form names a node that only a numeric key has.
  4. When k declares the factor axis, drop the term through feature_factor_key_msg.
  5. Otherwise rest must be a value and k names an asset or a group. Resolve it with resolve_axis_name and write one node per member. The natural value of a row is 1.0 when that row is the member and 0.0 when it is not.

Arguments

  • Z: The assets × features matrix the program writes, changed in place.
  • rows: The row indices of Z the term applies to.
  • target: One target of the grammar, or a vector of them.
  • sets: A UniverseSets object specifying the asset universe and groupings.
  • nx: The asset universe, sets.dict[sets.xkey], which indexes the rows of Z.
  • nz: The declared feature axis, sets.dict[sets.zkey], which indexes the columns of Z.
  • zidx: Map from a declared node name to its column of Z.
  • pool: The suggestion pool of feature_program_candidates.
  • strict: Whether an unresolvable name throws instead of warning.

Validation

  • A target that matches no production throws an ArgumentError carrying feature_grammar_msg, whatever strict says.

Returns

  • nothing. Cells written: for every row of rows, the column each named node occupies.

PortfolioOptimisers.feature_entry! — Function
feature_entry!(Z::Matrix{Float64}, entry::Pair, sets::UniverseSets, nx, nz, zidx, pool,
               strict::Bool) -> Nothing

Apply one entry of a graded feature program.

This is the dispatcher of the grammar, and its branch order is the disambiguation.

Algorithm

It recognises the grammar's entry production, entry := rowsel => targets | taxkey [=> group] => value. Julia's => is right-associative, so both forms arrive as a Pair whose right side may nest, and the branch order below separates them. It writes no cell itself: each branch hands the write to feature_diagonal! or to feature_target!.

  1. The left side is a taxonomy key and the right side bottoms out in a value — "nx_sector" => 2.0, "nx_country" => "UK" => 0.5. That is the diagonal, by decision: a bare value on the right of a taxonomy key always means "these rows, their own membership". Hand it to feature_diagonal!.
  2. The left side is a taxonomy key, the right side is g => tail with tail a target list, and g is itself a taxonomy key. Then g starts a target, so the left side is a bare row selector over the whole universe. Hand the whole right side to feature_target! over every row. This is the one genuine ambiguity in the grammar, and it is resolved by the same prefix rule everything else uses.
  3. The left side is a taxonomy key and the right side is g => tail with g no taxonomy key. Then g restricts the rows to those whose entry equals it, and tail is the target list. Drop the term through feature_missing_group_value_msg when no row matches.
  4. The left side is a taxonomy key and the right side is no Pair. It is then a target list over every row.
  5. Otherwise the left side is a row selector: resolve it with feature_rows, and apply the right side as a target list in that scope. An unresolved or empty scope writes nothing.

Arguments

  • Z: The assets × features matrix the program writes, changed in place.
  • entry: One entry of the program.
  • sets: A UniverseSets object specifying the asset universe and groupings.
  • nx: The asset universe, sets.dict[sets.xkey], which indexes the rows of Z.
  • nz: The declared feature axis, sets.dict[sets.zkey], which indexes the columns of Z.
  • zidx: Map from a declared node name to its column of Z.
  • pool: The suggestion pool of feature_program_candidates.
  • strict: Whether an unresolvable name throws instead of warning.

Returns

  • nothing. Cells written: whichever cells the production this entry matches writes, through feature_diagonal! or feature_target!.

Take an asset view of an asset-group membership matrix, or of a vector of matrices and estimators.

The matrix method slices columns, so it expects the groups × assets matrix asset_sets_matrix returns, whose column axis is the assets. It is not the method for the assets × features matrix asset_sets_features returns, whose column axis is the features and whose row axis is the assets. An estimator names a key rather than holding data, and the key is resolved after the view, so an estimator entry is carried through unchanged.

Algorithm

  1. For a matrix, return view(smtx, :, i), the columns of the selected assets.
  2. For a vector, take the view of each entry through the method that entry dispatches to, then narrow the element type with concrete_typed_array_if_abstract.

Arguments

  • smtx: A groups × assets membership matrix, or a vector whose entries are each such a matrix or an AssetSetsMatrixEstimator.
  • i: The asset index or range to slice.
  • args...: Additional positional arguments (ignored).
  • kwargs...: Additional keyword arguments (ignored).

Returns

  • For a matrix, a column view of size groups × length(i). For a vector, one result per entry, in the order of smtx, in a concretely typed array.
