PortfolioOptimisers.jl · measurement report · revision 3

The fold loop: keep the seam

Four shapes of cross_val_predict, measured for speed, inference and complexity. The seam costs nothing, and with three repairs applied it now matches the pre-seam code on dispatch and beats it on speed.

Date 2026-08-19 Julia 1.12.7, single thread, BLAS 1 Tools Chairmarks · JET · CodeComplexity Tests 1040 pass / 0 fail / 0 error

Verdict

The seam was right. Three repairs landed: D now ties the pre-seam code at zero in-loop dispatch and beats it on speed in seven of eight cases.

  • Runtime dispatch inside the loop machinery is zero, on all four schemes — matching B, which is the bar that mattered. C had 4.
  • D beats B in 7 of 8 end-to-end cases, by 2.5 % to 11.0 %, and allocates less in 6 of 8. B wins one, by 1.2 %.
  • Both defects were the same mistake twice: a compile-time fact passed as a run-time value. The element type as a keyword; the previous-weights flag as a Bool. Both are now type-level.
  • The Fold record is free and not measurable. Complexity, inference and harness time are identical to C. It buys naming, which no metric here scores. The honest claim is "free", not "better".
  • Loop shape still does not matter for speed. The whole harness costs 1 to 2 ns per fold in all four shapes. A real fold runs a portfolio optimisation.
  • v0.23.2 remains the least inferrable of the four: 114 runtime dispatches against D's 50, and it has no Pipeline subsystem to revert to.

working tree
A wholesale revert to v0.23.2 is not available

v0.23.2 has no src/23_Pipeline directory. The Pipeline subsystem and its three cross-validation entry points did not exist. It also has no TimeDependentContext, no per-fold asset view and no path_id, and it serialises a time-dependent walk-forward that the later versions run in parallel.

What changed in D

1 · ElT becomes a positional ::Type{ElT}

C forwarded the element type as a keyword value through two hops. The constant survived the first and died on the second, so Vector{ElT}(undef, n) became a runtime dispatch. JET named it exactly — the callee is the type constructor itself:

# C, walk-forward, inside #parallel_folds#1370(::Type, …)
runtime dispatch detected
  callee: Type{Vector{T}} where T  args: (undef, n)   # ← Vector{ElT}(undef, n)
- function parallel_folds(fit_fold, n, ex; ElT = PredictionResult)
+ function parallel_folds(fit_fold, n, ex, ::Type{ElT} = PredictionResult) where {ElT}

- function run_folds(fit_fold, opt, n, ex; ElT = PredictionResult, prev_w_flag = …)
+ function run_folds(fit_fold, opt, n, ex, ::Type{ElT} = PredictionResult;
+                    prev_w_flag::Bool = needs_previous_weights(opt)) where {ElT}

- function fold_loop(fit_fold, est, n, ex; …, ElT = PredictionResult, …)
+ function fold_loop(fit_fold, est, n, ex, ::Type{ElT} = PredictionResult; …) where {ElT}

That report is absent from D. Eleven call sites — the seven fold_loop sites and the four direct parallel_folds sites — now pass the element type positionally.

2 · The previous-weights flag becomes a ::Val{PW}

The same mistake, in a second place: a compile-time fact passed as a run-time value. As a Bool, the sequential branch of run_folds is inferred even for an optimiser that can never take it, and that branch reads an abstractly-typed predictions[i - 1]. As a type parameter the branch is eliminated.

- function run_folds(fit_fold, opt, n, ex, ::Type{ElT} = PredictionResult;
-                    prev_w_flag::Bool = needs_previous_weights(opt)) where {ElT}
-     if prev_w_flag
+ function run_folds(fit_fold, opt, n, ex, ::Type{ElT} = PredictionResult,
+                    ::Val{PW} = Val(needs_previous_weights(opt))) where {ElT, PW}
+     if PW   # compile-time constant: the branch is eliminated, not inferred

The default is safe because Val(needs_previous_weights(opt)) is settled by ordinary type inference, not constant propagation: it infers to Val{false}, and so survives any number of call layers.

3 · The callback takes one Fold

Five positional parameters is the point at which position stops being a readable contract. A reader at a call site saw do i, opti, rdi, tr, te and had to open fold_loop to learn what they were and in what order.

- predictions = fold_loop(opt, length(train_idx), ex; rd = rd, train_idx = train_idx,
-                         test_idx = test_idx) do i, opti, rdi, tr, te
-     return fit_and_predict(opti, rdi; train_idx = tr, test_idx = te, cols = cols)
- end
+ predictions = fold_loop(opt, length(train_idx), ex; rd = rd, train_idx = train_idx,
+                         test_idx = test_idx) do fold
+     return fit_and_predict(fold.est, fold.rd; train_idx = fold.train,
+                            test_idx = fold.test, cols = cols)
+ end

Fold is immutable, every field is concretely typed at its one construction site, and it is deliberately not TimeDependentContext: the context is what a schedule entry is resolved against, one step earlier and inside the loop, and it carries w_prev and path_id, which a callback must not read because they are already applied.

Why this table disagrees with the one above

D is the slowest shape here and the fastest end to end. Both are true, because the two tables measure different things.

This micro-benchmark hands every shape a concrete element type — ElT = Float64, because the stub returns a Float64 — and an estimator that is neither time-dependent nor previous-weights-hungry. Under those conditions neither defect can occur: Vector{ElT}(undef, n) is concrete in all four shapes, and the sequential branch is trivially dead. So this table measures only the structural overhead of the shape — the extra call layer D adds over B — and there D is honestly 46 ns slower over 60 folds.

End to end, the real element type is PredictionResult, a UnionAll, and the defects are live. That is what the fixes removed, and it is worth microseconds per call — three to four orders of magnitude more than the 46 ns of shape overhead it costs to get it.

Scale

One fold of a real backtest solves a portfolio optimisation — milliseconds to seconds with Clarabel. The harness costs nanoseconds. No choice among these four shapes can be justified on shape overhead alone.

Reading that table honestly

  • In-loop dispatch is zero, on every scheme. D ties B, which was the bar. C had 4. Total runtime dispatch fell 56 → 50.
  • B's zero was not craftsmanship, it was luck. Its call sites passed neither the element type nor the previous-weights flag, so both constants survived the single hop to their use. The seam added a hop and broke both. D restores them deliberately, at the type level, where no number of hops can lose them.
  • The recursion count rose, 2 → 12, all of it in MultipleRandomised. That scheme nests a fold loop inside a fold loop. Once the types are concrete, inference follows the chain round parallel_folds → path_fit_and_predict → fold_loop and meets its own recursion limit. In C the inner chain sat behind an abstract ::Type argument, so inference stopped before the recursion could form. Reaching a recursion limit is evidence the analyser got further, not that the code got worse — and that scheme's own dispatch count fell, 14 → 10, while its wall time fell 9.5 % and it allocated less.
  • v0.23.2 is the least inferrable by a wide margin, 114 runtime dispatches against B's 47, C's 56 and D's 50. The explicit form is not the inferrable one.
  • D's remaining +3 over B sits in Combinatorial (+1) and MultipleRandomised (+2). I diagnosed rather than assumed it — see below.

Why Combinatorial and MultipleRandomised do not match B's number

A per-scheme count is confounded: it moves when the analyser's reach moves. The metric that is not confounded is the union of distinct dispatch callees across all four schemes — the set of places in the package that actually dispatch.

D adds zero new dispatch sites in the fold loop. Every callee in D's union except one is also in B's. The per-scheme differences are the same sites appearing on more schemes, because the analysis now reaches them there. On MultipleRandomised, D reports three callees B does not — and none of the three is in the fold loop:

The three "extra" MultipleRandomised reports — where they live, and where B reports the same callee
calleeenclosing functionB reports it on
finalise_weight_bounds_optimise — the optimiser's own bodyCombinatorial, KFold, WalkForward

These three dispatches exist identically in B; B reports them on its other three schemes. What differs is only whether the analyser reaches them on this one. B's MultipleRandomised path runs parallel_folds(length(unique_ids), ex; ElT = MultiPeriodPredictionResult) with the element type as a keyword — abstract, and therefore a wall over everything beneath it: path_fit_and_predict, the per-fold fit_and_predict, _optimise. D's positional ::Type{ElT} removes the wall and the analyser walks through.

So B's lower MultipleRandomised count is under-reporting, not better code. finalise_weight_bounds and predict dispatch at run time on every fold of every path in B too. The wall-clock agrees: B is slower than D on that scheme, 0.1345 ms against 0.1217 ms, which it could not be if it genuinely dispatched less. D also removes one dispatch B has there, in sort_predictions!.

The one callee in D's union that is not in B's is lastindex(::AbstractVector). It is not in the fold loop, and it is not a consequence of the seam or of these repairs. B's source is different at that line.

# MultiPeriodPredictionResult's inner constructor
rd = getfield.(pred, :rd)        # pred::AbstractVector{<:PredictionResult} — abstract elements
…
B:    ivpa = rd[1].ivpa       # wrong fold — this is issue #187
C/D:  ivpa = rd[end].ivpa     # lowers to rd[lastindex(rd)] — one runtime dispatch

The change came from commit eaf4c4fe8f, "fix: collapse iv/ivpa as convex combinations, pair ivpa with its fold (closes #187)". ivpa is per-asset and cannot stack, so it must be taken from the last fold to pair with the last row of iv. Version C already carries it — the C-versus-B union differs by exactly this one call, and D inherits it unchanged.

So the honest accounting is: the fold-loop work adds no dispatch site at all. The single union difference between B and D is the price of an unrelated correctness fix, and reverting it to match B's number would reintroduce issue #187. Its root cause is worth noting for later, because it is the same shape as the ElT defect one level up: PredictionResult is a UnionAll used as a container element type, so anything read out of such a container is abstract. Fixing that is a change to a public result type, not to the fold loop.

The second defect, and the closing of it

Fixing ElT left two in-loop dispatches. JET named the line: the sequential branch of run_folds, fit_fold(i, i > 1 ? predictions[i-1] : nothing). ElT defaults to PredictionResult, a UnionAll and therefore abstract, so predictions[i-1] is abstractly typed and the call cannot resolve. That branch is dead for any optimiser that does not need the previous weights — but prev_w_flag was a run-time Bool, so inference analysed it anyway.

Making the flag a ::Val{PW} type parameter eliminates the branch instead of inferring it. The default Val(needs_previous_weights(opt)) is decided by ordinary type inference — it infers to Val{false} — so it survives the extra call layer that constant propagation of the Bool did not. Forwarding the Bool explicitly was tried first and measured: it changed nothing.

What I did not do

  • I did not fix the lastindex dispatch in MultiPeriodPredictionResult's constructor. It arrived with an unrelated correctness fix (issue #187) and its root cause — PredictionResult as a UnionAll container element type — is a separate piece of work on a public result type.
  • I did not run a MeanRisk and Clarabel benchmark. The solver dominates a fold by three to six orders of magnitude, so it cannot separate loop shapes. The isolated harness table does that instead.
  • I did not run the full test suite or a docs build. Those are the maintainer's to run.
  • I did not commit. The changes sit in the working tree of the shared dev checkout.
  • I did not run any of this in the shared kaimon REPL. Four package versions cannot share one process, so each ran in its own project and its own single-threaded process.
