2 · Three @argcheck sites destroy their own diagnostic when they fire

Strong errors
src/11_Phylogeny/05_NonHierarchicalClustering.jl:59 · src/08_Moments/22_StepwiseRegression.jl:141 · src/08_Moments/23_DimensionReductionRegression.jl:247
The check
@argcheck(isa(kwargs.weights, AbstractVector), TypeError)
Before — KMeansAlgorithm(; kwargs = (; weights = 1.0))
MethodError: no method matching TypeError(::String)
The type `TypeError` exists, but no method is defined for this
combination of argument types when trying to construct it.
After — the diagnostic survives
ArgumentError: `kwargs.weights` must be an AbstractVector of
observation weights, got Float64. Pass a vector of length
size(X, 1), or omit `weights` for an unweighted clustering.
Why

ArgCheck builds the exception by calling T(msg::String) on a bare exception type. Core.TypeError ships only two constructors — TypeError(where, expected::Type, got) and TypeError(func, context, expected::Type, got) — so the one-string call cannot resolve. The check works; only its failure path is broken.

Problem. The caller passes the wrong type for weights and sees an internal exception-construction failure. They never learn which argument was wrong, what was expected, or that weights was even the subject.

Direction. Replace the bare TypeError with an exception the library can construct from a message, and name the offending keyword and the type received.

  • signal: names the caller's keyword
  • blast radius: 3 sites
  • removes an unconstructible exception
  • failure path currently unreachable to read
