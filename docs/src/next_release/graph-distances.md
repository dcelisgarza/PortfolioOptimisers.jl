# [Graph distances, Exogenous Graphs, dependency exposure and seriation](@id migration-next-graph-distances)

## [Renamed keywords and changed defaults](@id migration-next-graph-distances-renames)

| Before | Now |
| --- | --- |
| The keyword `branchorder::Symbol` of `clusterise`, `phylogeny_matrix`, `optimise` of `HierarchicalEqualRiskContribution`, `NestedClustered`, `Stacking` and `SubsetResampling` | The field `branchorder` of the algorithm: `ClustersEstimator(; alg = HClustAlgorithm(; branchorder = BarJosephOrder()))` or `DBHT(; branchorder = ROrder())`. The three Symbols become singletons: `:optimal` is `OptimalLeafOrder()`, the default, `:barjoseph` is `BarJosephOrder()`, and `:r` is `ROrder()`. `nothing` gives the tree order. A graph verb that gets the keyword raises a `MethodError`. `optimise` absorbs the keyword in its `kwargs...`, so the call runs with the default order: move the order into the algorithm. |
| `DBHTs(D, S; branchorder = :optimal)`, and a Symbol with no method of its own, such as `:default`, to keep the merges that the hierarchy built | `DBHTs(D, S; branchorder = OptimalLeafOrder())`, and `branchorder = nothing` to keep the merges. A Symbol raises a `TypeError`. |
| `HierarchicalRiskParity` and `SchurComplementHierarchicalRiskParity` pinned the optimal leaf order, and a `branchorder` keyword had no effect | They read the leaf order of the branch order of their clustering algorithm. The default, `OptimalLeafOrder()`, gives the weights of the earlier release. A clustering with `branchorder = nothing` gives the tree order, the order of a SciPy linkage matrix. |
| `HClustAlgorithm(; linkage = :ward)`, the default, and `:single`, `:complete`, `:average` | `HClustAlgorithm(; linkage = WardLinkage())`, `SingleLinkage()`, `CompleteLinkage()`, `AverageLinkage()`. The tree is the same tree. A Symbol raises a `TypeError` at construction, where the earlier release built `HClustAlgorithm(; linkage = :nonsense)` and `clusterise` raised. |
| `HClustAlgorithm(; linkage = :ward_presquared)` | `HClustAlgorithm(; linkage = WardLinkage(; presquared = true))`. |
| No WPGMA, centroid or median linkage | `WeightedLinkage()`, `CentroidLinkage()` and `MedianLinkage()` give the trees of SciPy. The centroid and median trees have inversions, see [The cut of a dendrogram](@ref migration-next-graph-distances-cut). |
| `FeatureDistance()` measured with `AngularDist()`, `acos(cos) / π`, and its `sim` was `AngularSimilarity()` | `FeatureDistance()` measures with the new `ChordDist()`, `sqrt((1 - cos) / 2)`, and its `sim` is the new `ChordSimilarity()`, `1 - 2D²`. The chord is Euclidean, so the default Ward linkage is correct on it, and the angle is not Euclidean. Every distance moves, and the order of the pairs stays, because both metrics fall as the cosine rises. A single or a complete linkage gives the same tree with other heights. A Ward or an average linkage can give another tree, and so other weights. Write `FeatureDistance(; metric = AngularDist())` for the distances of the earlier release. |
| `RegressionPanel()`, a singleton type with no field, named its panel field `"loadings"` | `RegressionPanel(; name = nothing)` has one field, `name`. `nothing` gives `"loadings"`, and a non-empty string replaces it, so `FeatureDistance(; ape = RegressionPanel(; name = "beta"), sel = ["beta" => "mkt"])` selects one column. `RegressionPanel()` gives the panel of the earlier release. The positional constructor takes the name, `RegressionPanel(nothing)`, and the type has one parameter. A method that dispatches on `RegressionPanel` does not change. An empty string raises an `IsEmptyError`. |
| `PhylogenyPanel(; pl, alg)` named its panel field `"proximity"` | `PhylogenyPanel(; pl, alg, name = nothing)`. `nothing` gives `"proximity"`, and a non-empty string replaces it. The positional constructor takes three arguments, `PhylogenyPanel(pl, alg, name)`, and the type gains a third parameter. Its show prints the row `name ┴ nothing` last. An empty string raises an `IsEmptyError`. |
| The show of a parametric type whose every field holds `nothing`, such as `Proximity(; decay = nothing)`, printed the type parameters: `Proximity{Nothing}()` | It prints the name alone, `Proximity()`, as the show of a type with fields does. |
| `HierarchicalOptimiser(; cle = …)` for `HierarchicalRiskParity` and `SchurComplementHierarchicalRiskParity` | `HierarchicalRiskParity(; ser = HierarchicalSeriation(; cle = …))`, and the same keyword `ser` of `SchurComplementHierarchicalRiskParity`. `HierarchicalOptimiser` has no field `cle`, so the keyword raises a `MethodError`. The default `ser = HierarchicalSeriation()` gives the weights of the earlier release. `ser` also takes `SpectralSeriation()`, an order with no tree, or `FixedSeriationResult(; order)`, an order that you state. |
| `HierarchicalOptimiser(; cle = …)` for `HierarchicalEqualRiskContribution` | `HierarchicalEqualRiskContribution(; cle = …)`. HERC holds its clustering itself, and the weights do not change. |
| `res.clr` of a `HierarchicalRiskParityResult` or a `SchurComplementHierarchicalRiskParityResult` | `res.ser.clr` under the default seriation: `res.ser` is a `HierarchicalSeriationResult`, which holds the clustering in `clr` and the order in `order`. A spectral or a stated order has no clustering, so read `res.ser.order`. `res.clr` raises an `ErrorException` for a missing field. `res.clr` of a `HierarchicalEqualRiskContributionResult` does not change. |
| `TimeDependent` schedule on `HierarchicalOptimiser(; cle = …)` | A schedule of seriations on `HierarchicalRiskParity(; ser = …)` or `SchurComplementHierarchicalRiskParity(; ser = …)`, or of clusterings on `HierarchicalEqualRiskContribution(; cle = …)`. |
| `plot_network(pl, res::OptimisationResult; rd = pr)`, where the keyword `rd` took a prior result or a returns result | `plot_network(pl, res; pr = pr)` for the prior, and `plot_network(pl, res; rd = rd)` for the returns data, which an `ExogenousNetwork` reads. Pass both to draw a network over an exogenous graph from a prior of your own. A returns result in `rd` alone gives the figure of the earlier release. A prior in `rd` raises a `TypeError`. |
| A Pipeline step that writes a clustering, with HRP | The clustering goes into the `cle` of the `HierarchicalSeriation` in `ser`, where the earlier release put it into `opt.cle`. A Pipeline now also gives it to Schur, which the earlier release left out, and to HERC, through its own `cle`. A spectral seriation reads no tree, so it takes no clustering. |

## [The cut of a dendrogram](@id migration-next-graph-distances-cut)

`Clustering.cutree(clr.res; k)` throws a `BoundsError` on a tree of `CentroidLinkage()` or `MedianLinkage()` with an inversion, a merge lower than a merge below it, because it replays the merges in the order of their raw heights. Write `cut_dendrogram(clr.res, k)`. It cuts in the order of the cophenetic heights, so it always gives `k` clusters. On a tree with no inversion, it gives the labels of `Clustering.cutree`, so every result of the earlier release stays. `assignments(clr)`, the number of clusters, HERC and `ROrder()` read it. `clr.res.heights` keeps the raw heights, and `cophenetic_heights(clr.res)` gives the monotone form.

## [The returns data hold Exogenous Graphs](@id migration-next-graph-distances-graphs)

`ReturnsResult` and `PricesResult` hold named Exogenous Graphs: the names `ng` and one `ExogenousGraph` or `ExogenousGraphSeries` for each name in `G`. The keyword constructors take both with the default `nothing`, so code that builds the two types by keyword does not change.

- **`ReturnsResult`** has the fields `ng` and `G` after `E`, so its positional constructor takes fourteen arguments, `ReturnsResult(nx, X, nf, F, nb, B, ne, E, ng, G, ts, iv, ivpa, pnl)`, where the earlier release took twelve. Pass `nothing, nothing` after `E`, or use the keyword constructor.
- **`PricesResult`** has the fields `ng` and `G` after `E`, so its positional constructor takes ten arguments, `PricesResult(X, F, B, E, ng, G, iv, ivpa, pnl, span)`, where the earlier release took eight.
- **The type parameters** of both types gain two entries after the one of `E`. A method that names `ReturnsResult{…}` or `PricesResult{…}` with the parameters after `E` adds two `<:Any` entries.
- **The show** of both types prints the two fields `ng` and `G` after `E`. A doctest of your own that prints a `ReturnsResult` gains the two rows `ng ┼ nothing` and `G ┼ nothing`.
- **A returns result of your own** that subtypes `AbstractReturnsResult` holds no graph unless it adds the two fields. The user verbs read the graphs of a `ReturnsResult` and a `PricesResult` only.
- **`PredictionReturnsResult`**, the `rd` of a fold, has the fields `ng` and `G` after `E` too. A fold keeps the graphs of its test rows, so `dependency_exposure(pred)` reads the graph in force at each row of the fold. The positional constructor takes thirteen arguments, `PredictionReturnsResult(nx, X, nf, F, nb, B, ne, E, ng, G, ts, iv, ivpa)`, where the earlier release took eleven, and the type gains two parameters after the one of `E`. The keyword constructor takes both with the default `nothing`. The series of a path, `MultiPeriodPredictionResult.mrd`, holds no graph.

## [The slot of the linear constraints](@id migration-next-graph-distances-position)

The slot `lcse` also takes a `PositionConstraintEstimator` and its Result `PositionConstraint`, so a row can cap the gross, long or short position of a group, a factor or a node of a graph. A configuration without one does not change.

- **The resolved slot `lcsr`** of a `ResolvedConstraintBlock` can hold a `PositionConstraint` beside a `LinearConstraint`. Code that reads `lcsr.ineq` under a `PositionConstraintEstimator` reads `lcsr.lc.ineq`.
- **A vector `lcse` with an entry that wraps a vector, or with an entry whose every row dropped,** raised a `TypeError` at the resolution of the block. The resolved slot now holds the constraints of every entry in one vector, and leaves out a dropped entry.
- **`linear_constraints` on a vector of constraints** passes every keyword to its entries.

## [If you extend the library](@id migration-next-graph-distances-extending)

- **A position reading of your own, a subtype of `AbstractPositionReading`,** also reads a long-only book. A `ConcentrationLimit` read the weights there for every reading. It now calls `position_reading(pos, w, w, zeros)`, so a reading of the short part is zero.
- **An extension of `set_linear_weight_constraints!`** passes the weight bounds of its block in the keyword `wb` when it holds a `PositionConstraint`.
- **A branch order of your own is a subtype of `AbstractBranchOrder`**, which is public, with a method `PortfolioOptimisers.order_branches!(hmer::Clustering.HclustMerges, D, ::MyOrder)`. A method of `order_branches!(hmer, D, ::Val{:my_order})` is not called any more.
- **A linkage of your own is a subtype of `AbstractLinkage`**, which is public, with a method of `PortfolioOptimisers.linkage_symbol` for its label. A Lance-Williams linkage adds a method of `PortfolioOptimisers.lance_williams_update` and runs in the generic algorithm of the library. Any other linkage adds a method of `PortfolioOptimisers.linkage_merges` that returns its merges.
- **A seriation of your own is a subtype of `AbstractSeriationEstimator`**, which is public, with a method `PortfolioOptimisers.seriate(ser::MySeriation, X::PortfolioOptimisers.MatNum; dims::Int = 1, kwargs...)` that returns a subtype of `AbstractSeriationResult` with the property `order`. HRP and Schur read nothing else.
- **A rule of your own for an unknown entry, a subtype of `AbstractUnknownEntryRule`,** keeps its six methods for a factor attribution. The family has a second job: the rule of a `GraphUnion` and of `graph_union` for a part that has no graph in force. Your rule raises a `MethodError` there until it adds a method `PortfolioOptimisers.union_parts_in_force(rule::MyRule, known::AbstractVector{Bool})`, which returns the positions of the parts that the union sums, or `nothing` when the union is unknown. `KindwiseUnknown` has no such method.
- **A source of previous weights of your own, a subtype of `AbstractPreviousWeightsSource`,** keeps its methods for the fold loop. The family has a second job: the `src` of a `DependencyExposure`, which names the weights of a fold that the exposure describes. Your source raises a `MethodError` in `dependency_exposure` until it adds a method `exposure_weights(src::MySource, pred::PredictionResult, j::Integer = 1)`, which returns the rows of weights of member `j` and the row of the fold of each.
- **A constraint space of your own, a subtype of `AbstractConstraintSpace`,** can return a `PortfolioOptimisers.ConstraintBasis` from `constraint_space_basis`, with `nothing` as the key. The basis holds the matrix and the names of its columns, so the space needs no regression result and no key of a `UniverseSets`. Two optional methods join the interface: `PortfolioOptimisers.assert_space_constraint(space::MySpace, lce)` refuses a wrapped constraint at construction, and `PortfolioOptimisers.pipe_reads(space::MySpace)` states the slots of a pipeline step, `(:returns, :prior)` by default.
- **A separation of your own, a subtype of `AbstractSeparationAlgorithm`,** measures over an `ExogenousNetwork` when it adds two methods: `PortfolioOptimisers.separation_graph(sep::MySeparation, nte::ExogenousNetwork, X; kwargs...)`, and `PortfolioOptimisers.vertex_separations(sep::MySeparation, g, v)`, the separations from the vertex `v`. Over a `NetworkEstimator` it needs no new method.
- **A static graph and a series of graphs share the supertype `PortfolioOptimisers.AbstractExogenousGraph`.** The field `G` of a `ReturnsResult`, a `PricesResult` and a `PredictionReturnsResult` takes a vector of it, so a method of your own that takes an entry of `G` dispatches on it. `G = Any[g]` raises a `TypeError`. The family is closed: the views, the joins and the consumers read `ExogenousGraph` and `ExogenousGraphSeries` only.
- **A consumer of a graph of your own** reads the entries of its `ng` through `graph_names`, and an entry can be a `GraphUnion` as well as a name or `nothing`. The entry check of the user verb walks each entry with `PortfolioOptimisers.assert_consumer_entry`, which checks each part of a union. To read a union in a fit, call `PortfolioOptimisers.consumer_graph(consumer, rd, gu, dir)` with the single direction `dir` of the consumer. It gives one `ExogenousGraph`, as `consumer_graph(consumer, rd, name)` does for a name.
- **A method that dispatches on the type parameters of `HierarchicalRiskParity`, `SchurComplementHierarchicalRiskParity` or `HierarchicalEqualRiskContribution`** reads one more parameter: the field `ser`, or `cle` for HERC, is the second field, so the risk measure of HRP and the parameters of Schur are the third parameter. The positional constructors take the new field in the second place, and the positional constructors of `HierarchicalResult`, `HierarchicalRiskParityResult` and `HierarchicalEqualRiskContributionResult` move `clr` out of the core into the HERC Result and put `ser` into the HRP Result.
